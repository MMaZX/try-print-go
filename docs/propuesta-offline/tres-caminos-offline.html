USQAY Print · decisión de arquitectura

Tres caminos para el modo offline real

Cuando no hay internet, ¿cómo llega un trabajo de impresión desde Electron hasta la estación correcta entre N máquinas de la LAN? Tres propuestas alternativas — se elige una.

Electron/Next (rest_web_react) → Laravel → usqay-print-server (nube) → WebSocket → usqay-print-client → impresora ✕ sin internet, esto se corta acá

El frontend ya asume http://localhost:9100/print como agente local — pero eso solo funciona si Electron y la impresora están en la misma máquina. Con N estaciones en N máquinas, se rompe.

Lo que ya existe y no hay que rehacer

Investigar antes de proponer encontró más piezas construidas de las que parecía a primera vista.

usqay-print-clientResiliencia offline (épica 5): config cacheada en SQLite, reintentos con backoff, impresión sin conexión activa.
electron/sync/sync-engine.jsOutbox de pedidos/cobros/inventario ya en SQLite local, con sync contra /tenant/sync/offline e idempotency_key.
lib/print-dispatch.tsContrato PrintJob ya tipado y compatible con el renderer del cliente Go — y ya asume un agente local en :9100.
usqay-print-serverProtocolo Register/Config/PrintJob/Sync por WebSocket, ya validado en LAN pura esta semana.

Comparación

PropuestaIdea centralEsfuerzoCuándo conviene
① Agente HTTP + registroCada estación abre :9100/print; Electron guarda terminal_id → IPBajoLocales chicos, salir rápido
② Descubrimiento mDNSLas estaciones se anuncian solas en la LAN, sin IPs a manoMedioVarias estaciones, IPs por DHCP
③ Hub embebidoElectron levanta su propio usqay-print-server como sidecar en la LANMedio-altoEscala real, un solo protocolo

Recomendación

Empezar por la Propuesta 1 para no bloquear lo que depende de esto hoy — reutiliza el contrato que el frontend ya tiene escrito. La Propuesta 3 es el destino final si el número de estaciones crece: comparten la mitad del trabajo (el agente Go necesita HTTP entrante en ambas), así que empezar por la 1 no es tiempo perdido. La Propuesta 2 se suma encima de cualquiera de las otras el día que mantener IPs a mano se vuelva un problema real.

1
Agente HTTP local + registro de estaciones en LANEl cambio más chico posible sobre lo que ya existe en los dos repos

Cumplir literalmente el contrato que rest_web_react ya tiene escrito (localhost:9100/print), generalizado a toda la LAN: cada usqay-print-client abre su propio servidor HTTP, y Electron guarda a qué IP corresponde cada terminal_id.

Flujo

sequenceDiagram
    participant E as Electron (POS, sin internet)
    participant R as local_estaciones (SQLite)
    participant A as usqay-print-client (cocina-01, :9100)
    participant P as Impresora física

    E->>R: ¿IP de terminal_id = "cocina-01"?
    R-->>E: 192.168.1.42
    E->>A: POST http://192.168.1.42:9100/print
    A->>A: repo.Insert (misma cola SQLite del worker)
    A-->>E: 200 OK
    A->>P: Worker imprime ESC/POS (ciclo ya probado)

Cambios por repositorio

usqay-print-client/internal/localapi/server.go — nuevo
mux.HandleFunc("POST /print", func(w http.ResponseWriter, r *http.Request) {
    var job PrintJobPayload
    json.NewDecoder(r.Body).Decode(&job)
    repo.Insert(queue.PrintJob{ID: job.JobID, Payload: string(job.Payload), ...})
    w.WriteHeader(http.StatusOK)
})
go http.ListenAndServe("0.0.0.0:9100", mux)
rest_web_react/lib/print-dispatch.ts — una función nueva
function resolveAgentUrl(terminalId: string): string {
  const estacion = getEstacionLocal(terminalId) // lee local_estaciones
  return `http://${estacion?.ip_lan ?? 'localhost'}:${estacion?.puerto ?? 9100}/print`
}

Todo lo demás — postToAgent, el reintento de print-retry.js — sigue igual, porque el contrato PrintJob no cambia.

Riesgos

RiesgoImpactoMitigación
Firewall de Windows bloquea :9100 entranteAltoRegla de firewall en el instalador NSIS
IP cambia por DHCPMedioIP fija por MAC, o migrar a Propuesta 2
Sin autenticación en :9100/printBajo en LAN cerradaToken compartido por header si hace falta

Esfuerzo: 1 archivo nuevo en el cliente Go (~60-80 líneas), 1 tabla SQLite + 1 función en el frontend. Sin tocar usqay-print-server ni el protocolo WebSocket.

2
Descubrimiento automático (mDNS / zeroconf)Las estaciones se anuncian solas, nadie configura IPs a mano

Misma base que la Propuesta 1 (cada agente expone :9100/print), pero cada estación se anuncia sola en la red local y Electron arma el mapa terminal_id → IP automáticamente, en vivo — la misma tecnología que usa una impresora AirPrint o un Chromecast.

Flujo

sequenceDiagram
    participant A as usqay-print-client (cocina-01)
    participant N as Red local (multicast)
    participant E as Electron (POS)

    A->>N: Anuncio mDNS "_usqayprint._tcp" cada pocos segundos
    E->>N: Escucha continua de anuncios
    N-->>E: cocina-01 @ 192.168.1.42:9100
    E->>A: POST http://192.168.1.42:9100/print
    A-->>E: 200 OK

Cambios por repositorio

usqay-print-client — main.go, con github.com/grandcat/zeroconf
server, _ := zeroconf.Register(
    cfg.TerminalID, "_usqayprint._tcp", "local.", 9100,
    []string{"terminal_id=" + cfg.TerminalID}, nil,
)
defer server.Shutdown()
electron — con bonjour-service
const bonjour = new Bonjour()
bonjour.find({ type: 'usqayprint' }, (service) => {
  estaciones.set(service.txt.terminal_id, { ip: service.referer.address, puerto: service.port })
})

local_estaciones pasa de fuente de verdad a caché de la última vez vista — útil como fallback si mDNS falla en algún router.

Riesgos

RiesgoImpactoMitigación
Routers con "AP isolation" filtran multicast entre equiposAlto si pasaDocumentar requisito de red; mantener tabla manual como fallback
Firewall de Windows (mDNS + :9100)MedioReglas en el instalador, igual que Propuesta 1
Nueva dependencia en ambos reposBajo-medioLibrerías maduras, protocolo estándar (RFC 6762/6763)

Esfuerzo: se construye encima de la Propuesta 1 (no la reemplaza) — agregar zeroconf/bonjour-service y cambiar de dónde sale el mapa de IPs.

3
Hub local embebido en ElectronUn solo protocolo online/offline, el que ya está probado

En vez de un contrato HTTP que solo existe para offline, se reutiliza el WebSocket de usqay-print-server — ya probado en LAN pura esta semana. Electron levanta ese mismo binario como sidecar (igual que ya hace con el server Next.js), y cada estación se conecta ahí cuando no hay internet, con el mismo protocolo de siempre.

Flujo

sequenceDiagram
    participant E as Electron (POS)
    participant H as Hub local (usqay-print-server sidecar, :8080)
    participant C as usqay-print-client (cocina-01)
    participant P as Impresora física

    E->>H: POST /api/v1/jobs (mismo endpoint que Laravel usa online)
    H->>C: PrintJobMsg por WebSocket (mismo protocolo de la nube)
    C->>P: Imprime ESC/POS (Autoridad de Impresión Local, épica 5)
    C-->>H: sync (job impreso)
    Note over C,H: Al volver el internet, C reconecta solo
a wss://app.usqay.com (server_urls[0])

Cambios por repositorio

electron/main.js — nuevo sidecar, mismo patrón que startNextServer()
printHub = spawn(hubBinPath, [], { cwd: hubConfigDir, env: process.env })
// bind 0.0.0.0 — otras máquinas de la LAN deben poder llegar
usqay-print-client/internal/ws/connection.go — server_urls con failover
{
  "server_urls": ["wss://app.usqay.com/ws", "ws://192.168.1.50:8080/ws/agent"],
  "terminal_id": "cocina-01"
}
// Run() recorre la lista en orden; el backoff de la épica 5 ya existe,
// solo cambia a qué URL apunta cada reintento.

El hub resuelve impresoras en orden: Laravel (si responde) → config estática local → última config cacheada — mismo principio que la config cacheada del cliente (story 5.1), ahora también en el servidor.

Riesgos

RiesgoImpactoMitigación
Si la máquina del hub se apaga, cae la impresión de todas las estaciones offlineAltoElegir como hub la máquina que menos se apaga; a futuro combinar con mDNS para elegir hub dinámicamente
Resolver impresoras sin Laravel es trabajo nuevoMedioEmpezar solo con config estática, cacheo automático en 2ª iteración
Empaquetar un binario Go en 3 plataformasMedioasarUnpack/extraResources ya es un patrón usado hoy para el server Next.js

Esfuerzo: el más alto de los tres (~3-5 días entre los dos repos), pero un solo protocolo para siempre en vez de mantener WS + HTTP en paralelo — es la que mejor sostiene el crecimiento.
