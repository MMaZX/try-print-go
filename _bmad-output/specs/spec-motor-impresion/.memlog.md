- (direction) Spec creada desde el informe de investigación técnica 2026-07-15 (flujo acordado: investigar → spec); alcance ambas plataformas; el usuario exige decisiones únicas, funcionales y escalables
- (decision) Motor de layout: box model propio en Go con IR de dos pasadas (measure→arrange) e híbrido texto+raster selectivo; HTML/CSS descartado (wkhtmltopdf archivado 2023, CVE-2022-35583) y PDF intermedio descartado (go-pdfium sobredimensionado)
- (decision) Windows: mantener RAW vía alexbrainman/printer; DEVMODE/XFORM/AddCustomPaperSize no aplican a RAW (Windows los ignora) y quedan reservados a una futura vía GDI para inkjet/láser
- (decision) Linux: mantener lp -o raw para térmicas; filtros CUPS solo para inkjet/láser (vía printText existente)
- (decision) Capacidades: DeviceProfile declarativo (patrón escpos-printer-db); resolución perfil explícito → derivado del ancho declarado (58→384, 80→576 como defaults) → fallback 58mm; sin autodescubrimiento porque el spooler es unidireccional (GS I inviable)
- (constraint) Go puro sin CGO en todo el pipeline; únicas dependencias nuevas fogleman/gg y golang.org/x/image (ambas Go puro), solo desde fase 3
- (constraint) Build tags por SO intactos (printer_windows.go/printer_linux.go); el pipeline de layout es portable, sin syscalls
- (constraint) Contrato JSON PrintPayload es premisa fija: los payloads existentes siguen imprimiendo sin cambios
- (constraint) Fase 1 exige equivalencia byte a byte con el renderer actual; desde fase 2 los diffs golden solo pueden ser intencionales
- (constraint) Texto nativo ESC/POS por defecto; raster selectivo por bloque, nunca ticket completo rasterizado por defecto (peso 50-100KB vs 1-4KB)
- (constraint) Features de hardware (cut, drawer, QR nativo, GS L/W) condicionadas por flags del perfil con fallback (mitiga firmware genérico con soporte parcial)
- (constraint) Binario del cliente sin crecer más de 3MB hasta fase 3 inclusive
- (capability) CAP-1 suite golden de bytes ESC/POS sobre el renderer actual (matriz 58/80/custom × padding × tablas-merge) como red de seguridad previa al refactor
- (capability) CAP-2 DeviceProfile declarativo que resuelve geometría y features por impresora; equivalencia byte a byte con salida actual para 58/80mm
- (capability) CAP-3 motor box model measure→arrange con restricción maxWidthDots; desborde de contenido imposible por construcción; padding calculado en un único punto
- (capability) CAP-4 backend texto emite encuadre físico vía GS L/GS W desde la IR, sin espacios manuales
- (capability) CAP-5 backend raster selectivo: gg + fuente monoespaciada embebida + threshold 50% + empaquetado GS v 0 para logos y precisión sub-carácter
- (capability) CAP-6 modo captura .prn por flag de config: vuelca los bytes exactos de Print() a archivo para verificación sin hardware
- (decision) Fase 4 (TCP 9100 + GS I) queda explícitamente fuera del contrato como no-goal opcional futuro
- (assumption) Threshold ~50% como binarización por defecto: los tickets llevan logos, no fotos (Floyd-Steinberg solo si aparecen fotos)
- (assumption) 203 DPI como resolución de referencia mm→dots (unidad de movimiento default GS P en térmicas comunes)
- (assumption) Los defaults de perfil 58mm→384 dots y 80mm→576 dots (valores de fabricante Epson) son válidos multi-marca
